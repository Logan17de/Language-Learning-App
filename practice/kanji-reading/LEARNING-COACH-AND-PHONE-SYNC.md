# Kanji Learning Coach: retention-first protocol and phone sync

Updated: 2026-10-15 (JST)
Repository: https://github.com/Logan17de/Language-Learning-App/tree/main/practice/kanji-reading
Current authorized ceiling: **JLPT N2** (N5–N2 included, N1 excluded). This does not imply completion or mastery of lower levels.

## Source of truth and exact-target isolation
- Treat each **full vocabulary target** as independent: `compound|特色` and `kana|帰す` are distinct cards. Missing `compound|特色` NEVER demotes `single|特`, `single|色`, or any other card. Character-level statistics require separate direct evidence and must not be inferred as full correctness from a compound answer.
- Phone uploads its observed card state to `app-sync/current.json`. **Do not edit this file to push changes to the phone.** It is a phone-owned snapshot and will be overwritten by subsequent phone syncs.
- Coach-to-phone state changes go only into `app-sync/overrides.json` with exact `targetType|target` keys, a supported `state` of `mastered`, `familiar`, `weak`, or `unknown`, and a **new unique `revision` for every intended update**. The phone applies each revision once when the user taps Sync. Never downgrade a word just because it appears in a story; use explicit learner feedback or graded answers.
- A missing card in `current.json` does **not** prove the app lacks the vocabulary: unreviewed cards may be absent from the uploaded rating snapshot. Verify the exact target in `data/kanji-recall-v32/compound/N5-*.json` through `N2-*.json` or `data/kanji-recall-v32/kana-kanji/N5-*.json` through `N2-*.json` before deciding whether a `compound|...` or `kana|...` override is possible. Never invent a card or change a `single|...` state from a word-in-context miss.
- At each story-feedback turn, perform the coach-to-phone override merge immediately for all newly justified matching exact cards, even if the user hasn't opened the phone; preserve earlier revisions and log pending confirmation.
- The existing phone app syncs **card memory-state overrides only**. It does **not** download this instruction, coach statistics, stories, exercises, session plans, or schedules. Keep these in the repository and chat; do not claim they appear in the V33 interface. A phone UI feature for those requires a separate app update, while preserving the V32 study interface.

## Evidence and tracking
After each **completed, graded** practice session, preserve an append-only answer/event log with session id, timestamp, exact target key, JLPT level, question type (reading/meaning), response, correctness, and provenance (phone vs chat). Distinguish explicit incorrect answers from words merely reported difficult. Do not invent missing attempt events or dates. Deduplicate already-ingested phone events using stable event identifiers where available; if the app snapshot lacks individual attempt events, record only supported aggregates and mark missing dates unknown.

Maintain independently for each directly tested character and each exact vocabulary card:
- total appearances, correct, incorrect, success rate, last seen, last correct, last incorrect
- confidence score (0–100, based on graded evidence and recency) and forgetting score (0–100, based on recency, recent misses and downward trend)
- recent outcome sequence, reading-vs-meaning accuracy, source, and next due completed-session number
- unknown/unassessed distinct from an observed incorrect response

**Classification based on graded accuracy:** Mastered if >=90% with >=5 appearances; Familiar 70–<90%; Weak 40–<70%; Critical <40%. Below 5 appearances do not promote to Mastered; other classifications are provisional. If zero graded appearances, classify as Unassessed, not Critical. The phone's four existing memory buttons are **not automatically equivalent** to binary graded correctness. Preserve them as self-reported states unless a real grading rule is recorded. Map Critical to phone `weak` only when explicitly warranted; the phone has no Critical state.

## Review scheduler
- Default target mix for eligible graded items: 50% Weak, 25% Critical, 15% Familiar, 10% Mastered. When a category is underpopulated, redistribute to due items and unassessed items transparently; do not fabricate Critical cards to fill quota.
- Rotate: A → B → C → D → A, never repeatedly drill the same target back-to-back. Prefer >=3 different targets between repetitions when possible.
- After a miss, schedule review at +1, +3, +7, +14 **completed sessions** (not calendar days). After demonstrated repeated success, use +7, +14, +30 sessions. Do not reset overdue items merely because time elapsed. Respect actual completed-session counter.
- Detect forgetting via declining rolling accuracy, consecutive misses, long time since last correct, and regression after a previously successful delay. Move demonstrated regressions back to active review and report why.
- Prefer delayed recall, interleaving, contextual use, and months-long retention over short-term quiz scores.

## Story-first workflow

**Explicit advance requirement (learner request, 2026-10-15):** After the learner reports difficulty, record and sync it, then stop. **Never generate, display, or activate the next story unless the learner explicitly says “next story” or clearly requests another story.** Prepared story `N5N4-002.md` remains on hold until expressly requested. Asking to update statistics or phone sync does NOT authorize story advancement. The user studies reported words independently; do not explain reading/meaning unless explicitly asked.

- User reads a short, memorable Japanese story using N5–N2 characters only, then reports exact difficult words. Do not automatically treat reading the story as a graded answer.
- Prioritize weak and critical exact targets in funny, visual, emotional, or absurd but natural stories. Mix familiar/mastered words for support. Avoid N1. Add furigana or English meanings **when the user asks**; otherwise retain the established no-furigana story-first workflow.
- Space target repetitions, including within stories; do not place the same weak target repeatedly in consecutive prompts.
- Following every completed session, give a report with Summary (score, accuracy, questions), Strongest, Weakest, Forgetting Risks, Recommended Review Set, Story Review (short story plus meanings when requested), and Next Session Focus.

## Git workflow after each completed session
1. Read latest `app-sync/current.json`, existing coach progress, story feedback, and completed-session ledger. Avoid treating older exports as newer phone data.
2. Append verified outcomes, recalculate metrics and due schedule, and update `progress.json`, `word-review-stats.json`, and/or a dedicated per-event ledger without losing historical evidence.
3. For **explicit** card state changes intended for the phone, merge into `app-sync/overrides.json` without deleting unrelated pending overrides. Use exact key and unique revision, e.g.:
```json
{
  "compound|特色": {
    "state": "weak",
    "revision": "coach-2026-10-15-session-0001-特色"
  }
}
```
This example is illustrative only; do not insert it without new graded evidence. Preserve the override file's existing envelope (`format`, `schemaVersion`, `updatedAt`, `notes`, `overrides`).
4. Commit verified updates using `kanji-progress: update stats after practice YYYY-MM-DD`.
5. Tell the user to tap **Sync now** in V33. Verify the next `current.json` upload before claiming phone application; a GitHub commit alone does not prove that the phone received it.

## Continuous monitoring limits
Check for new uploads on a recurring schedule when enabled. Compare against last processed snapshot, report new evidence, and avoid duplicate grading or Git commits when nothing changed. Background checks are not instantaneous, and phone changes are visible only after the phone syncs. Never claim a live phone update without confirmation.
